# Persistence in Java Microservices

## Choosing an access layer

Don't default to JPA out of habit. The right tool depends on how much control
you need over the SQL and how relational your domain actually is.

| Approach | When it wins | When it hurts |
|---|---|---|
| **Spring Data JPA / Hibernate** | Rich object graphs, lots of CRUD, you want caching, dirty checking, lazy loading | Complex reporting queries, bulk operations, anything where you keep fighting the ORM to get the SQL you want |
| **Spring Data JDBC** | Simple aggregates, you want mapping without ORM machinery (no proxies, no lazy loading, no session) | Multi-level object graphs — it deliberately doesn't do lazy loading or cascading the way JPA does |
| **JdbcClient / JdbcTemplate** | You want to write SQL and map rows yourself, no magic | Boilerplate mapping grows with entity count; no change tracking |
| **jOOQ** | Complex, dynamic, typed SQL — reporting, analytics, query builders assembled at runtime | Commercial license for non-OSS databases (Oracle, SQL Server); a real learning curve |
| **MyBatis** | Existing codebase already on it, or hand-written SQL with XML/annotation mapping preferred over a DSL | Greenfield services — jOOQ or JdbcClient cover the same need with less ceremony |
| **Hibernate directly (no Spring Data)** | You need Hibernate-specific features (`@BatchSize`, multi-tenancy, custom types) without repository magic | Most teams don't need this — Spring Data JPA already delegates to Hibernate underneath |

Rule of thumb: **Spring Data JPA is the default** for typical CRUD services with
real object graphs. Reach for JdbcClient or jOOQ the moment you're writing native
queries just to work around the ORM, or the moment a "simple" `@Query` needs three
joins and a window function. Spring Data JDBC is the middle ground when your
aggregates are small (order + line items, not a twelve-entity graph) and you want
predictable, explicit SQL without hand-writing every mapper.

## Entity mapping

```java
@Entity
@Table(name = "orders")
public class Order {

    @Id
    @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "order_seq")
    @SequenceGenerator(name = "order_seq", sequenceName = "order_seq", allocationSize = 50)
    private Long id;

    @Column(name = "customer_id", nullable = false)
    private String customerId;

    @Enumerated(EnumType.STRING)               // NEVER EnumType.ORDINAL — see below
    @Column(nullable = false, length = 20)
    private OrderStatus status;

    @Convert(converter = MoneyConverter.class)
    @Column(name = "total_amount", nullable = false)
    private Money totalAmount;

    @Version                                    // optimistic locking
    private Long version;

    // equals/hashCode below — deliberately NOT generated by Lombok @Data
}
```

### ID generation: SEQUENCE beats IDENTITY

| Strategy | Behavior | Batching |
|---|---|---|
| `IDENTITY` | DB assigns the ID on insert; Hibernate must flush immediately to know it | **Defeats JDBC batching** — Hibernate cannot batch inserts because it needs each row's generated key before it can build the next statement |
| `SEQUENCE` + `allocationSize` | Hibernate pre-allocates a block of IDs (e.g. 50) from the sequence in one round trip, then assigns them in memory | Fully batchable — no per-row round trip |
| `UUID` (`GenerationType.UUID` or app-assigned) | No DB round trip at all; ID known before insert | Batchable, but random UUIDs fragment b-tree indexes (Postgres, MySQL) — prefer UUIDv7/ULID-style time-ordered generation if you go this route |

**Default to `SEQUENCE` with a real `allocationSize`.** `IDENTITY` feels simpler
(`AUTO_INCREMENT`/`SERIAL`, no extra DB object) but it silently disables batch
inserts — Hibernate has no choice but to `INSERT` one row at a time, wait for the
generated key, then move to the next. On a hot insert path this is a 5-10x
throughput difference, not a rounding error. `allocationSize = 50` means one
sequence round trip buys 50 in-memory IDs; just make sure it matches on both the
`@SequenceGenerator` and the actual DB sequence's `INCREMENT BY`, or you'll get
gaps or collisions.

### `@Column` explicitness

Don't rely on Hibernate's naming strategy and defaults to guess your schema.
Write `name`, `nullable`, `length`, `precision`/`scale` explicitly. It's not
verbosity for its own sake — it's the difference between a schema mismatch
failing at `Configuration` validation time vs. failing in production with a
truncated string or a silent `NULL`.

### `@Enumerated(EnumType.STRING)` — never ORDINAL

```java
public enum OrderStatus { CREATED, PAID, SHIPPED, CANCELLED }
```

With `ORDINAL` (the historical default before people learned better), Hibernate
stores the enum's **position** (`0`, `1`, `2`, `3`) in the column. The failure
mode: someone inserts a new status in the middle —

```java
public enum OrderStatus { CREATED, REFUNDED, PAID, SHIPPED, CANCELLED }
//                                  ^ inserted here — everything after shifts
```

— and every row that was `PAID` (ordinal 1) is now read back as `REFUNDED`
(the new ordinal 1). No exception, no migration failure, no log line. Data is
just silently wrong, and you find out from a customer complaint weeks later.
`STRING` stores the literal name; it's slightly more bytes on disk and that's the
entire cost. There is no scenario where `ORDINAL` is worth that risk.

### AVOID Lombok `@Data` on entities

`@Data` generates `equals()`/`hashCode()`/`toString()` over **every field**,
and a mutable `@Setter` on every property. On a JPA entity this causes three
separate problems:

1. **`equals`/`hashCode` over all fields** means two entities compare unequal
   the instant any field changes — including collections that trigger lazy
   loading during `hashCode()`, which throws `LazyInitializationException`
   outside a session.
2. **Before the entity is persisted**, `id` is `null`. If `equals`/`hashCode`
   include `id`, the object's hash code changes the moment it's saved
   (`null` → generated value) — putting it in a `HashSet` before save and
   looking it up after save fails, because it's now in the wrong bucket.
3. **`toString()` over all fields** walks lazy associations and either throws
   or triggers N+1 loading just from a log statement.

The fix: hand-write `equals`/`hashCode` on the **business/natural key** if one
exists, or fall back to a stable surrogate-key comparison that tolerates a
`null` id gracefully:

```java
@Override
public boolean equals(Object o) {
    if (this == o) return true;
    if (!(o instanceof Order other)) return false;
    return id != null && id.equals(other.id);   // never equal until persisted
}

@Override
public int hashCode() {
    return getClass().hashCode();                // stable before AND after persist
}
```

This looks unintuitive (two never-saved `Order`s are always unequal to each
other, and hashCode never reflects identity) but it's the only version that
doesn't break under a `Set`/`Map` across the persist lifecycle. `@Getter` alone
is fine; skip `@Data`, `@Setter` on entities (mutability via setters undermines
invariants anyway — prefer intention-revealing methods), and `@EqualsAndHashCode`
without `onlyExplicitlyIncluded` restricted to the id.

## Relationships & N+1 — the most important section

### EAGER is the default you don't want

```java
@ManyToOne(fetch = FetchType.LAZY)              // ALWAYS specify — default is EAGER
@JoinColumn(name = "customer_id")
private Customer customer;

@OneToMany(mappedBy = "order", fetch = FetchType.LAZY)   // OneToMany defaults LAZY already
private List<OrderLine> lines = new ArrayList<>();
```

The trap: `@ManyToOne` and `@OneToOne` default to `FetchType.EAGER`.
`@OneToMany` and `@ManyToMany` default to `LAZY`. Most people assume all
associations default to lazy, write `@ManyToOne` with no `fetch`, and get an
unconditional join (or an unconditional secondary `SELECT`) on every single
load of the owning entity — including code paths that never touch `customer`
at all. **Always write `fetch = FetchType.LAZY` explicitly on every
`@ManyToOne`/`@OneToOne`**, so the fetch strategy is a decision, not an
accident of the spec's historical defaults.

Never make a **collection** `EAGER`. An eager collection is fetched every time
the owner loads, with no way to opt out per query, and two eager collections on
the same entity force Hibernate into a cartesian product.

### Fixing N+1

N+1 is: load N orders, then Hibernate lazily fires one additional query per
order to fetch its `customer`. Options, from most to least targeted:

```java
// 1. JOIN FETCH in JPQL — one query, eagerly joins for THIS query only.
@Query("SELECT o FROM Order o JOIN FETCH o.customer WHERE o.status = :status")
List<Order> findByStatusWithCustomer(@Param("status") OrderStatus status);

// 2. @EntityGraph — declarative, reusable, keeps the repository method's
// return type honest without a JPQL string.
@EntityGraph(attributePaths = {"customer", "lines"})
List<Order> findByStatus(OrderStatus status);

// 3. @BatchSize — not zero N+1, but N/batchSize queries instead of N.
// Good default for associations you sometimes need and can't always JOIN FETCH.
@BatchSize(size = 25)
@OneToMany(mappedBy = "order", fetch = FetchType.LAZY)
private List<OrderLine> lines;

// 4. Projections/DTOs — skip the entity graph problem entirely by selecting
// only the columns you need. Best option when you don't need managed entities.
public record OrderSummary(Long id, String customerName, BigDecimal total) {}

@Query("""
    SELECT new com.example.myservice.OrderSummary(o.id, c.name, o.totalAmount)
    FROM Order o JOIN o.customer c WHERE o.status = :status
    """)
List<OrderSummary> summarize(@Param("status") OrderStatus status);
```

Use projections whenever the result is going straight to a response DTO — it's
strictly cheaper than loading full entity graphs you're about to discard.

### `MultipleBagFetchException`

```java
// Throws MultipleBagFetchException at query execution:
@Query("SELECT o FROM Order o JOIN FETCH o.lines JOIN FETCH o.payments WHERE o.id = :id")
Order findWithLinesAndPayments(@Param("id") Long id);
```

Fetching two `List` (bag) collections in one query produces a cartesian
product Hibernate can't safely dedupe — hence the exception. Two fixes:

- **Change the collection type to `Set`** instead of `List`, if order doesn't
  matter or you can sort at the application layer — Hibernate can fetch
  multiple `Set`s in one query.
- **Split into separate queries** — fetch `lines` in one call, `payments` in
  another (or use `@EntityGraph` with subgraphs which Hibernate handles more
  gracefully than raw multi-collection `JOIN FETCH`). This is usually the
  simpler and more predictable fix.

### Pagination + `JOIN FETCH` on a collection = in-memory pagination

```java
// Hibernate logs "HHH90003004: firstResult/maxResults specified with collection
// fetch; applying in memory!" — it fetched ALL matching rows, then paginated
// the Java list. For a large table this is a memory and latency disaster.
@Query("SELECT o FROM Order o JOIN FETCH o.lines WHERE o.customerId = :cid")
Page<Order> findByCustomer(@Param("cid") String cid, Pageable pageable);
```

The fix is the two-query id-then-fetch pattern: paginate on IDs only (no
collection join, so pagination happens in the database), then fetch the full
graph for just that page's IDs:

```java
@Query("SELECT o.id FROM Order o WHERE o.customerId = :cid ORDER BY o.id")
Page<Long> findIdsByCustomer(@Param("cid") String cid, Pageable pageable);

@Query("SELECT o FROM Order o JOIN FETCH o.lines WHERE o.id IN :ids ORDER BY o.id")
List<Order> findByIdsWithLines(@Param("ids") List<Long> ids);

// Service layer glues them together:
public Page<Order> ordersForCustomer(String customerId, Pageable pageable) {
    Page<Long> idPage = repo.findIdsByCustomer(customerId, pageable);
    List<Order> orders = repo.findByIdsWithLines(idPage.getContent());
    return new PageImpl<>(orders, pageable, idPage.getTotalElements());
}
```

## `@Transactional`

Put the boundary at the **service layer**, not the repository (repositories
should be composable inside a larger unit of work) and not the controller
(HTTP concerns have no business dictating transaction scope).

```java
@Service
public class OrderService {

    @Transactional(readOnly = true)             // hints the driver/Hibernate:
    public Order findOrder(Long id) {            // no dirty checking, no flush,
        return repo.findById(id).orElseThrow();  // some drivers route to a replica
    }
    // NOTE (Spring Boot 4.1+): a @Transactional method that ends up NOT querying
    // -- cache hit, early return, empty input list -- still checks out a physical
    // connection for its whole duration under the default eager fetch. On a
    // read-heavy service that is pool capacity burned on nothing. Fix globally:
    //     spring.datasource.connection-fetch=lazy
    // which wraps the DataSource in LazyConnectionDataSourceProxy so a connection
    // is acquired only when a statement actually executes. Measure before/after;
    // `eager` restores the old behaviour.

    @Transactional(rollbackFor = Exception.class)   // see rollback rules below
    public Order placeOrder(NewOrderRequest request) {
        Order order = new Order(request);
        repo.save(order);
        outboxRepo.save(OutboxEvent.orderPlaced(order));   // same TX — see outbox below
        return order;
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void auditIndependently(String action) {
        // Runs in its own transaction — commits/rolls back independent of the
        // caller's transaction. Use for audit logs you want to keep even if the
        // calling operation fails.
        auditRepo.save(new AuditEntry(action));
    }
}
```

| Propagation | Behavior |
|---|---|
| `REQUIRED` (default) | Join the caller's transaction if one exists; otherwise start a new one |
| `REQUIRES_NEW` | Always start a new transaction, suspending the caller's — used for "this must commit independently" (audit trails, idempotency markers written even on failure) |

### Rollback rules — the huge trap

**By default, Spring only rolls back on unchecked exceptions**
(`RuntimeException` and `Error`). A checked exception thrown from inside a
`@Transactional` method **commits the transaction anyway**, checked exception
and all, unless you say otherwise:

```java
// WRONG: throws a checked exception — Spring commits the transaction as if
// nothing happened, because InsufficientStockException isn't a RuntimeException.
@Transactional
public void reserveStock(Order order) throws InsufficientStockException { ... }

// RIGHT: be explicit about what rolls back.
@Transactional(rollbackFor = Exception.class)
public void reserveStock(Order order) throws InsufficientStockException { ... }
```

Default to `rollbackFor = Exception.class` on anything that isn't a pure
`readOnly` query, or use unchecked exceptions for your domain errors in the
first place (the more common modern style) so the default rollback behavior
does the right thing without annotation tuning.

### Self-invocation bypasses the proxy

```java
@Service
public class OrderService {

    public void processAll(List<Order> orders) {
        orders.forEach(this::placeOrder);   // this. — NOT going through the proxy.
    }                                        // @Transactional on placeOrder is a no-op here.

    @Transactional
    public void placeOrder(Order order) { ... }
}
```

`@Transactional` (like `@Cacheable`, `@Async`) is implemented as a proxy
wrapping the bean. A call from **inside the same class** goes directly to the
method, never through the proxy, so the annotation is silently ignored — no
warning, no exception, just a method that runs without a transaction. Fix by
calling through another bean, or by self-injecting the proxy
(`@Lazy` self-reference / `AopContext.currentProxy()` with
`exposeProxy = true`).

### Never call external I/O inside a transaction

```java
// WRONG: holds a DB connection (and any locks it took) for the full duration
// of an HTTP call to a partner service. If the HTTP call hangs, the connection
// is pinned — under load this starves the connection pool.
@Transactional
public void placeOrder(Order order) {
    repo.save(order);
    paymentClient.charge(order);            // network call inside a DB transaction
    queueClient.publish(new OrderPlaced(order.getId()));   // same problem
}
```

Two independent failure modes: (1) the external call is slow or hangs and the
DB transaction — and the connection and any row locks it holds — stays open
the whole time; (2) the external call succeeds but the transaction then rolls
back for an unrelated reason, and now a partner has been charged or a message
published for an order that doesn't exist. The fix is the **outbox pattern**:
write the intent (an `OutboxEvent` row) in the *same* transaction as the
business change, commit, and let a separate poller or CDC process do the
actual network call/publish after the commit is durable. See the messaging
reference for the full outbox table shape.

## HikariCP

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 20      # see sizing formula below — NOT "as large as possible"
      minimum-idle: 5
      connection-timeout: 3000   # ms to wait for a connection before giving up
      idle-timeout: 300000       # 5 min — evict idle connections above minimum-idle
      max-lifetime: 1500000      # 25 min — MUST be shorter than any DB/LB/pooler
                                  # idle/session timeout in front of it
      leak-detection-threshold: 30000   # log a stack trace if a connection is
                                          # checked out longer than 30s — a leak signal
```

### Pool sizing

The classic starting formula (from HikariCP's own wiki, still a reasonable
default): `connections = ((core_count * 2) + effective_spindle_count)` per
pool. In practice on cloud infra, "spindle count" is 0 for SSD/NVMe, so it
collapses to roughly `cores * 2` as a *starting point to load test from*, not
a formula to trust blindly.

The number that actually matters: **your database's `max_connections`,
divided by the number of service replicas, minus headroom for migrations,
admin tooling, and other services sharing the database.** A pool of 50 per
instance across 10 replicas is 500 connections — check that against what the
database (or the pooler in front of it, e.g. PgBouncer/RDS Proxy) can actually
hold before it starts rejecting connections or thrashing. **Bigger is not
better** — a larger pool just means more concurrent statements competing for
the same finite CPU/IO on the database; past the point of saturation, adding
pool capacity adds queueing delay, not throughput.

### `maxLifetime` vs upstream idle timeouts

If a load balancer, proxy, or the database itself silently closes connections
older than *T*, and `maxLifetime` is longer than *T*, Hikari hands out a
connection it thinks is healthy but which the network path has already
dropped — the query fails with a broken-pipe-shaped error that looks like a
random flake. **Always set `maxLifetime` a few minutes shorter than the
tightest timeout anywhere in the connection path** (DB `wait_timeout`, LB idle
timeout, connection pooler timeout) so Hikari retires connections before
anything else does.

### Virtual threads change the bottleneck

With platform threads, thread pool size and DB pool size were both natural
concurrency limits, roughly matched. With virtual threads (Java 21+), you can
have thousands of virtual threads in flight — the thread pool is no longer the
constraint, so **the JDBC connection pool becomes the real bottleneck**, and
sizing it correctly matters more, not less. A blocking JDBC call still pins
the *carrier* thread for its duration (JDBC drivers aren't yet virtual-thread
aware for their blocking I/O), so the pool size is your effective concurrency
ceiling regardless of how many virtual threads are queued behind it.

For a Loom-native pool, **Agroal** (used by Quarkus) is built with virtual
threads in mind and worth evaluating if HikariCP's thread-pinning behavior
under heavy virtual-thread load becomes a measured problem — but don't switch
preemptively; HikariCP remains the correct default until you have a profiled
reason to move.

## Batching & bulk operations

```properties
spring.jpa.properties.hibernate.jdbc.batch_size=50
spring.jpa.properties.hibernate.order_inserts=true
spring.jpa.properties.hibernate.order_updates=true
```

- `batch_size` groups statements into one JDBC batch round trip instead of one
  round trip per row.
- `order_inserts`/`order_updates` reorder pending operations so all inserts to
  the same table are contiguous — without this, Hibernate flushes in the order
  operations happened in code, which can force a table switch every row and
  defeat batching even with `batch_size` set.
- **`IDENTITY` generation defeats all of this** (see ID generation above) —
  batching and `IDENTITY` are mutually exclusive in Hibernate.

`saveAll()` is not automatically a bulk operation — it's a loop over
individual `save()` calls (a `merge`/`persist` each) that batching
configuration turns into fewer round trips; it does **not** become a single
`INSERT ... VALUES (...), (...), (...)` statement, and each entity still goes
through the full lifecycle (dirty checking, version increment, cascades,
listeners). For a genuine bulk update/delete across thousands of rows where
you don't need entity lifecycle callbacks, drop to a `@Modifying @Query`
(JPQL bulk update) or straight JDBC — it's a different, much cheaper
operation:

```java
@Modifying
@Query("UPDATE Order o SET o.status = :status WHERE o.status = :from")
int bulkTransition(@Param("from") OrderStatus from, @Param("status") OrderStatus status);
```

Note `@Modifying` bulk updates bypass the persistence context — entities
already loaded in the current session will be stale until you
`clear()`/refetch.

## Migrations

| | Flyway | Liquibase |
|---|---|---|
| Format | Plain SQL (primarily) | XML/YAML/JSON/SQL, DB-agnostic changesets |
| Style | Write the SQL yourself, versioned filenames | Declarative changes, can generate DB-specific SQL from one changeset |
| Rollback | Forward-only by convention (community edition) | First-class rollback changesets |
| Best fit | Teams comfortable writing raw SQL per dialect | Teams needing DB-portability or auditable rollback definitions |

Either is fine; pick one and be consistent about naming
(`V{version}__{description}.sql` for Flyway) so migration order is
unambiguous from the filename alone.

**Never run migrations from application startup with N replicas.** If your
migration tool runs in a `@PostConstruct`/`ApplicationRunner` and you deploy 5
replicas, you get 5 concurrent migration attempts racing for the same schema
lock — best case they serialize awkwardly and slow down startup, worst case
you hit a tool-specific edge case with concurrent lock acquisition and a
replica crashes on boot. Run migrations as a **separate step**: a Kubernetes
`Job`/init container that runs once before the deployment rolls, or a distinct
CI/CD pipeline stage — never as a side effect of the app's own boot sequence
scaled to N.

### Expand-contract for rolling deploys

During a rolling deploy, old and new code run **simultaneously** against the
same database for the duration of the rollout. A migration that both adds and
removes something in one step breaks whichever version is still running the
old code. The fix is to split every breaking schema change into ordered,
independently-deployable steps:

1. **Expand**: add the new column/table, nullable or with a default — old code
   ignores it, new code doesn't need it yet.
2. **Deploy code that writes to both** old and new columns (dual-write), or
   backfills existing rows.
3. **Deploy code that reads from the new column**, still writing both.
4. **Backfill** any remaining rows written before step 2.
5. **Deploy code that stops writing/reading the old column.**
6. **Contract**: drop the old column, once you're certain no running instance
   (including any rolled-back version) still touches it.

Renaming a column is the classic case this saves you from: never `RENAME
COLUMN` directly on a live rolling deploy — old code's SQL references the old
name and breaks the instant the rename lands, regardless of which pod happens
to serve the next request. Expand-contract turns it into "add new, dual-write,
cut over, drop old."

### `CREATE INDEX CONCURRENTLY` (Postgres)

A plain `CREATE INDEX` takes a lock that blocks writes to the table for the
duration of the build — on a large table, minutes of blocked writes. `CREATE
INDEX CONCURRENTLY` builds without that lock, at the cost of taking roughly
2x as long and not being usable inside a transaction block (Flyway/Liquibase
migrations that run in a wrapping transaction need to mark that migration as
non-transactional). Always use it for indexes added to tables already serving
production traffic.

## Testing

**Use Testcontainers with the real database**, not H2. H2's SQL-mode
compatibility layers (`MODE=PostgreSQL`, etc.) are an approximation, not a
faithful engine — they accept syntax the real database rejects, reject syntax
the real database accepts, and silently diverge on things like `CASCADE`
behavior, JSON operators, window function edge cases, and locking semantics.
A green test suite against H2 tells you your JPQL parses; it tells you nothing
reliable about whether your query runs correctly against the database you
actually deploy to.

```java
@Testcontainers
@SpringBootTest
class OrderRepositoryTest {

    @Container
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:17")
            .withDatabaseName("myservice_test");

    @DynamicPropertySource
    static void datasourceProperties(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", postgres::getJdbcUrl);
        registry.add("spring.datasource.username", postgres::getUsername);
        registry.add("spring.datasource.password", postgres::getPassword);
    }

    @Test
    void findsOrdersByStatus() {
        // runs against real Postgres — the same dialect quirks as production
    }
}
```

Run the same Flyway/Liquibase migrations against the Testcontainers instance
that run in production, so schema drift between "what the test expects" and
"what the migration actually produces" gets caught before deploy.

## Checklist

- [ ] Chose the access layer (JPA / Spring Data JDBC / JdbcClient / jOOQ / MyBatis) based on how relational the domain is, not by default
- [ ] Every `@ManyToOne`/`@OneToOne` has an explicit `fetch = FetchType.LAZY`
- [ ] No `EAGER` collections anywhere
- [ ] `@GeneratedValue` uses `SEQUENCE` with a real `allocationSize` (or app-assigned UUID), not `IDENTITY`, on any table with meaningful insert volume
- [ ] Every `@Enumerated` is `EnumType.STRING`
- [ ] No `@Data`/`@Setter`/all-fields `@EqualsAndHashCode` on entities; `equals`/`hashCode` based on id only
- [ ] N+1 checked for on hot paths — `JOIN FETCH`, `@EntityGraph`, `@BatchSize`, or a DTO projection
- [ ] No `JOIN FETCH` on a collection combined with `Pageable`/`firstResult`/`maxResults`
- [ ] `@Transactional` boundaries are at the service layer, with `rollbackFor` set where checked exceptions matter
- [ ] No external HTTP/queue calls inside a `@Transactional` method — outbox pattern used instead
- [ ] Verified no self-invocation of `@Transactional`/`@Cacheable` methods within the same class
- [ ] HikariCP `maximum-pool-size` sized against the DB's `max_connections` ÷ replica count, not guessed
- [ ] HikariCP `max-lifetime` shorter than every upstream idle/session timeout
- [ ] `hibernate.jdbc.batch_size` + `order_inserts`/`order_updates` set, and confirmed compatible with the ID generation strategy
- [ ] Migrations run as a separate Job/pipeline step, never from app startup with N replicas
- [ ] Any breaking schema change (rename/drop/type change) uses expand-contract, not a single-step migration
- [ ] Large index builds on live tables use `CREATE INDEX CONCURRENTLY` (Postgres) or the dialect equivalent
- [ ] Tests use Testcontainers against the real database engine, not H2, for anything dialect-sensitive
